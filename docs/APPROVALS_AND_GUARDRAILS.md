# Approvals, Permissions and Safety Guardrails

## 1. Approval gates in this prototype

| Gate | What is reviewed | What happens if approved | What happens if rejected |
|---|---|---|---|
| Business question | Is this the right business problem and is it actionable? | The workflow may train a candidate model | Workflow stops before model training |
| Model promotion | Are the holdout metrics, sample size and model signals acceptable for the next controlled stage? | Candidate is marked ACTIVE in the demo registry | Workflow stops; no writeback stage |
| Business-system writeback | Is this exact batch and destination acceptable? | Prediction records are marked SYNCED in the synthetic CRM score extension | Scores remain unsynchronized |

An approval is specific to one stage. Approving the business question does not approve the model. Approving the model does not approve writing scores to CRM.

## 2. What an agent may do without approval

In the prototype, the workflow may:

- Read the synthetic tables through the defined connector functions.
- Count and profile records.
- Suggest business questions.
- Train candidate models after the business-question approval.
- Calculate holdout metrics.
- Save a model artifact and internal pending prediction rows.
- Prepare a proposed impact summary.
- Record workflow progress and learning notes.

## 3. What requires an approval gate

- Starting model development for the selected business objective.
- Promoting a candidate into the active model slot.
- Synchronizing prediction results to a business-system endpoint.

The demo endpoints are not connected to a real CRM or ERP. A production version must add identity-aware approval authorization. It must not assume that a user who can open the dashboard has permission to approve every business action.

## 4. Prohibited behavior

Do not allow the model or an agent to:

- Invent missing source data or silently change a business definition.
- Treat a probability as a guaranteed outcome.
- Infer sensitive attributes without a specific lawful and approved basis.
- use model outputs as the sole basis for employment, credit, insurance, medical, legal or other high-impact individual decisions.
- Delete or overwrite business records without an explicit approved operation and recovery plan.
- Send communications, offer discounts, change prices, alter accounts or move money without the relevant authorization.
- Bypass a required review because an LLM said that the result is safe.
- execute arbitrary code generated by a model on a system containing secrets or production data.

## 5. Supervisor instructions in the demo

The following instructions are parsed as deterministic, narrow controls:

| Instruction | Implemented effect |
|---|---|
| `prioritize recall` | Decision threshold becomes 0.35 |
| `prioritize precision` | Decision threshold becomes 0.65 |
| `do not use FIELD` | Excludes the named known feature if it exists |
| `exclude FIELD` | Excludes the named known feature if it exists |

The threshold is a demonstration setting. It is not universally optimal. It affects the precision/recall trade-off and must be measured and approved.

Other text is stored and supplied as context to the optional language-model adviser. The project does not dynamically convert arbitrary prose into permissions, executable SQL or write actions. This is intentional: instructions that change security or business policy must be translated into reviewed, tested code or a configuration with a clear owner.

## 6. Audit information

The demo stores:

- Workflow identifier, objective, status and timestamps.
- Supervisor instructions.
- Graph state and pending approval request.
- Each approval decision and comments in the resumed graph state.
- Candidate model record, metrics and artifact path.
- Prediction records and whether they were synchronized.
- Business impact review and feedback events.

For production, extend this with authenticated actor identity, role, source IP/device context where appropriate, request/correlation IDs, policy version, connector identity, exact changed records, before/after values, model and data versions, prompt/tool versions and immutable audit retention.

## 7. Security baseline before real connections

1. Replace demo credentials and use a secrets manager.
2. Require sign-in and role-based access control.
3. Separate read-only data connectors from write-capable service identities.
4. Restrict API routes, network paths, source tables and columns.
5. Validate every input and output; use parameterized database access.
6. Treat documents, database text and API results as data, not trusted instructions.
7. Protect the agent from prompt injection by limiting tools and permissions.
8. Use isolated execution environments for any generated code.
9. Log and alert on denied access, unusual volume, failed approvals and unexpected writes.
10. Back up the database, checkpoint store and artifacts; test restoration.
11. Conduct privacy, security, compliance and model-risk reviews before deployment.
12. Maintain a manual fallback and a kill switch for each integration.

## 8. Model-specific controls

- Confirm the business label and prediction horizon.
- Check that all input fields exist at the time the prediction is made.
- Check that related entities do not leak across train/test partitions.
- Test on a future time period where appropriate.
- Review quality by relevant groups and segments.
- Check calibration if probabilities are used for decisions.
- Monitor missingness, data drift, model performance and business outcomes.
- Define when to retrain, pause or roll back.
- Preserve the previously approved model.
- Require a human to approve model changes that can affect customers.

## 9. Incident response

When an agent produces an unexpected action or output:

1. Stop the affected workflow or connector.
2. Disable write access if an external system may be affected.
3. Preserve run IDs, logs, source references and artifacts.
4. Notify the named process and security owners.
5. Determine which records/actions were affected.
6. Correct or roll back using an approved procedure.
7. Identify whether the cause was data, model, prompt, tool permission, workflow or human process.
8. Add a test that prevents recurrence.
9. Re-enable only after the owner approves the remediation.

## 10. Explicit demo limitation

The dashboard currently relies on a local network boundary and does not implement enterprise user authentication or approver identity verification. Never expose it publicly or connect it to production systems as-is. The Compose password and service configuration are demonstration defaults.
